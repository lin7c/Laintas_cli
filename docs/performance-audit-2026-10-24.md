# laintas-cli 性能检查（2026-10-24）

仍有明确的优化空间。最值得先改的是发送请求前重复计算整段上下文的 token，其次是每轮同步快照和长会话保存。源码启动入口也能明显减轻。以下是代码检查、本机基准和仅在基准进程中做的对照实验；没有修改运行时代码或用户配置。

## 范围与方法

- 检查对象：`0583b22` 加工作区原有未提交修改，Python 3.12.3、Linux 源码运行环境。
- 每个计时用例预热一次，再取 5 次中位数。机器并非独占，毫秒数应按数量级理解。
- 启动最终数据、token 预检对照和快照对照均串行运行。较早的存储测试与一组启动测试有重叠，其墙钟数据只作定位参考，另记录了 CPU 时间和 profile。
- 消息样本：每条 2048 个字符，内容为重复的中英文测试行，并附消息序号。1000 条是本地会话存储的压力样本；它不代表模型每轮实际收到的上下文大小。
- 所有写入都定向到任务专属临时目录；启动测试使用临时 `LAINTAS_HOME` 和字节码缓存。没有调用真实模型或修改真实账户、会话、偏好设置。
- 未测 Windows GUI、PyInstaller 发行包、真实模型响应时间或公网 TLS 往返，结论中的启动数字仅适用于这里的源码入口。

## 1. 优先消除同一检查阶段的重复 token 计数

相关位置：`agent_loop.py:6688`、`:6978`、`:7229`、`:13207`、`:13215`、`:13223`，`tokenizer.py:108`。

`tokenizer.count_messages()` 每次都会把整个消息数组转成 JSON，再完整分词。在开启辅助 AI、上下文未达到压缩阈值且没有待发布摘要的常见路径中，发送前检查对同一数组完整计数 4 次：

1. `_coordinate_compaction()` 判断前台压缩阈值。
2. 同一函数再次计算 `tokens`。
3. 主循环检查压缩后的上下文是否超限。
4. `_publish_context_headroom()` 更新剩余空间。

单次分词用实装的 `cl100k_base` 测量；对照实验调用当前检查函数，关闭后台摘要启动，并把预算固定到足够大，以保证消息在阶段内完全不变。复用版本只在该基准进程中缓存这个未变化数组的结果。

| 样本 | 实际 token 数 | 当前检查阶段 | 复用一次计数的对照 | 完整计数次数 |
| --- | ---: | ---: | ---: | --- |
| 64 条消息 | 41,986 | 124.15 ms | 36.19 ms | 4 → 1 |
| 256 条消息 | 167,938 | 653.69 ms | 150.46 ms | 4 → 1 |

这个检查阶段的对照降幅约 71%–77%，不是整个任务的提速比例。单独计数的中位数分别约 31 ms 和 144 ms。

建议先让检查函数返回、传递或复用已计算的 token 数，确保预算校验仍使用同一套分词结果。若扩展到跨轮缓存，必须在摘要发布、分页淘汰、消息原地修改、模型或编码器变化时失效；仅用消息条数作缓存键会读到旧值。

## 2. 每轮上下文快照有可避免的扫描和读回

相关位置：`laintas_cli.py:10670`，`agent_loop.py:13895`，`context_snapshot.py:272`、`:363`、`:549`。

主循环每次请求都会建立 `context_capture`。传输前先通过 JSON 往返复制完整 payload，返回后同步写上下文快照。存储侧又会复制、编码内容，并在写完后立即展开返回值：重新读取、验 hash、解析刚存下的 blob。主循环没有使用这个展开返回值。

此外，`_apply_retention()` 在每次 append 后读取所有会话 manifest、寻找未引用 blob，并遍历目录统计总大小。200 个很小的会话就能形成约 43 ms 的一次保留扫描。

在已有 200 个会话、写入 256 条消息的串行对照中：

| 路径 | 中位数 |
| --- | ---: |
| 当前 `append_call()` | 72.40 ms |
| 仅省去调用方不用的展开返回值 | 62.74 ms |
| 再跳过本次完整保留扫描的实验对照 | 34.51 ms |

最后一行只用于分离成本。正式实现仍需执行保留策略和容量限制，不能直接删除 GC。profile 中一次 append 的 93 ms 里，约 48 ms 花在 `_apply_retention()`。

较早的存储压力测试中，1000 条消息的请求复制约 52 ms，`append_call()` 约 216 ms。这是更大的压力样本，不能与上表直接相减。

建议先加兼容默认行为的可选轻量返回路径，再用增量空间统计、manifest 索引及有界清理减少每轮全量扫描。保留写入原子性、内容验证和可追溯记录；如果后续改成后台写入，需单独处理快照冻结、队列顺序和退出刷盘。

## 3. 长会话同步仍重复复制并存储同一份状态

相关位置：`session_store.py:367`、`:442`，`laintas_cli.py:24761`。

已有优化让 live 文件和 current 文件共用一次序列化，但以下开销仍存在：

- `sync_runtime()` 深拷贝两份 state，`save_session()` 随后又深拷贝两份 state；其中包含整个 `_thread_messages`。
- 文件同时存储 `state`、`agent_state` 和 `chat_history`。合成样本里的单个 1000 条会话文件约 7.21 MB，live 和 current 各保存一份完整内容。
- 即使内容没变，跳过写入之前仍已完成这些复制、编码和 hash。

| 合成消息数 | 内容未变：墙钟 / CPU | 内容变化：墙钟 / CPU |
| --- | ---: | ---: |
| 100 | 60.61 / 31.93 ms | 34.14 / 30.27 ms |
| 500 | 101.45 / 93.48 ms | 174.65 / 150.85 ms |
| 1000 | 182.28 / 169.91 ms | 299.58 / 260.88 ms |

100 条样本的墙钟反序反映了调度波动，不能解释成未变化路径固有地更慢。1000 条未变化样本的 profile 总计 353 ms，其中深拷贝累计约 177 ms，序列化及 hash 路径约 166 ms；profile 本身也有额外开销。

建议先明确一次保存的快照所有权，减少调用链中的重复深拷贝，同时保持调用方修改不能污染已保存快照的约束。后续可评估磁盘 schema 只保存一份权威 state、current 使用引用；这些需要兼容旧会话格式，并覆盖恢复、分支、删除及并发指针更新。不要用去掉 fsync 来换取这部分收益。

## 4. 源码入口和同步启动检查可以减轻

相关位置：`laintas_cli.py:78`、`:29387`、`:29825`，`setup.py` 的 `console_scripts`，`updater.py:245`。

当前 `/usr/local/bin/laintas-cli` 用 venv Python 直接执行 `laintas_cli.py`。这个文件为 31,544 行、1,429,127 字节，Python 需要先解析整份文件，之后才会执行文件顶部的 `--version` 快捷分支。单独编译整份文件的中位数约 1.02 秒，说明提前返回不能省去大文件解析。

最终串行复测，依赖字节码已预热，结果如下：

| 入口 | 中位数 | 5 次范围 |
| --- | ---: | --- |
| 当前源码 `--version` | 943.00 ms | 852.96–973.23 ms |
| 当前源码 `--help` | 1692.08 ms | 1550.02–2079.31 ms |
| 模拟 setuptools 入口的 `--version` | 1098.42 ms | 988.15–1374.37 ms |
| 只导入 `version.py` 的轻量入口对照 | 81.16 ms | 76.64–94.31 ms |

setuptools 入口先导入 `laintas_cli` 再调用 `main()`，也无法走仅适用于 `__main__` 的版本快捷分支。

建议用小入口处理版本、帮助和其他轻量命令，再延迟导入交互栈，并让安装入口与源码入口共用它。普通交互启动仍需要交互栈，不能拿版本对照的 81 ms 当作完整 REPL 的启动目标。

启动时 `check_update_available()` 仍在主线程调用 requests，配置超时为 1.5 秒；这个参数也不是包括 DNS、多地址连接和读取在内的全流程硬上限。可缓存更新结果或在首个 prompt 可用后检查。孤儿 worktree 清理和扩展加载也在启动路径上，但本次未量化其真实成本。

## 其他可用空间

- 默认 `loop_delay=0.2`，成功工具步骤之间仍有固定等待。可通过 `/config loop_delay 0` 调整；`_adaptive_loop_delay()` 对失败仍保留至少 0.8 秒退避、对重复步骤至少 1 秒退避。30 次正常等待累计约 6 秒。本次没有改用户设置。
- 模型传输使用顶层 `requests.post()`，可评估按账户、目标和线程隔离的连接池，减少连续调用的新建连接。没有做公网对照，暂不承诺 TLS 或首包收益；必须继续保持官方、自定义后端及直连路由的认证边界。
- 流式预览已经限制到 10 Hz，没有证据支持优先重写整个终端渲染层。

## 建议落地顺序

1. 复用同一发送前检查阶段的 token 结果，保持压缩与预算判断一致。
2. 快照按需展开返回值，并减少每轮完整保留扫描。
3. 会话保存减少重复深拷贝，再单独评估兼容性的存储格式调整。
4. 提取轻量启动入口，更新检查移出首个 prompt 的关键路径。

不同测试覆盖的阶段、样本和触发频率不同，不能把所有毫秒数直接相加成每轮的保证收益。
